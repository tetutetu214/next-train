> MVP（東京メトロ1社）の確定仕様。段階2の拡張余地は残すが、ここではメトロ前提で書く。

## 2. 表示ルール（確定）

- **対象範囲**: 現在地から半径1km以内。
- **表示駅数**: 近い順に最大5駅（メトロは駅が密集するため上限を設ける）。0駅なら「近くに対象駅がありません」。
- **複数路線が乗り入れる駅**: 駅×路線ごとにカードを分ける（次発は「路線×方面」単位で意味を持つため。同じ表参道でも銀座線と千代田線は別カード）。
- **方面**: 上り（▲ ascending）/ 下り（▼ descending）の2ブロック。`odpt:railDirection` の生IDは出さず自然言語名に変換。
- **各方面に表示する本数**: 次発1本（MVP）。余裕があれば次々発まで2本。
- **終電後**: その方面に現在時刻以降の発車が無ければ「本日の運行終了」。
- **「あと何分」**: 現在時刻と発車時刻の差を分で表示。1分未満は「まもなく」。

## 3. カレンダー区分の判定（確定）

- ODPTの時刻表は `odpt:Calendar:Weekday`（平日）と `odpt:Calendar:SaturdayHoliday`（土休日）に分かれる。
- 判定: 土曜・日曜・**祝日**なら SaturdayHoliday、それ以外は Weekday。
- 祝日判定: npm の軽量ライブラリ（例 `japanese-holidays`）で判定。理由＝内閣府CSVを自前で取り込む手間を省け、依存も小さい。年末年始の特殊ダイヤはMVPでは扱わない（2区分で割り切る）。

## 4. Workersプロキシ API設計（確定）

ブラウザはODPTを直接叩かず、必ずWorkers経由。Workersが `acl:consumerKey` を付与。

- `GET /api/stations`
  - 東京メトロの全駅（駅ID・駅名・緯度経度・所属路線）を返す。
  - ブラウザ側で `localStorage` にキャッシュ（駅は頻繁に変わらない）。日次程度で更新。
- `GET /api/timetable?station=<駅ID>&railway=<路線ID>&calendar=<区分>`
  - 指定駅・路線・カレンダー区分の方面別時刻表を返す。
  - レスポンスは必要項目だけに整形（departureTime / destination名 / trainType名 / railDirection名）。
- 共通: CORSヘッダ付与、ODPTエラー時は素直にステータス透過。

## 5. データ整形（Workers側に寄せる）

ODPTのIDは機械可読IDなので、表示用の自然言語名へ変換してから返す:
- `odpt:destinationStation` の駅ID → 駅名（stations辞書を引く）
- `odpt:trainType` のID → 種別名（各停/急行など）
- `odpt:railDirection` のID → 方面名（`odpt:Railway` の ascending/descendingRailDirection 対応で上り下りも判定）

ブラウザは整形済みデータを並べるだけにし、処理を軽くする。

## 6. 非機能要件

- **HTTPS必須**（Geolocationの secure context 制約）。ローカル開発は localhost で可。
- 駅一覧はクライアントキャッシュし、起動毎に `/api/stations` を叩かない。
- 時刻表は駅カード表示時に取得し、同一区分は短時間キャッシュ。
- レート制限対策: 近傍5駅×路線分のみ取得。全駅ポーリングはしない。

## 8. テスト方針（振る舞いで書く）

- `geo.ts`: 「2点の距離をHaversineで正しく算出する」「1km境界の内外を正しく判定する」。
- `timetable.ts`: 「現在時刻以降で最も早い発車を返す」「終電後は運行終了を返す」「土曜は土休日ダイヤを選ぶ」「祝日は土休日ダイヤを選ぶ」。
- モック方針: ODPTレスポンスのサンプルJSONを固定して使う（外部API依存をテストに持ち込まない理由をコメントで明記）。
